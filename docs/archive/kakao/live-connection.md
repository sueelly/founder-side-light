이메일·코드 헤더를 포함한 합성 잘못된 신원 POST도 401이었습니다. 이는 잘못된 인증 정보가
거부됐다는 뜻이며, 실제 참가자 코드 없이 새 헤더 인증의 성공까지는 확정할 수 없습니다.
실제 참가자 제출은 없습니다.
[확인 기록 JSON](operator-check.json)에 시각·응답 코드·로컬 계약 검증 결과를 저장했습니다.
캐시를 우회해 반복 확인했으며 응답에도 `Cache-Control: no-store`가 있었습니다.
운영측 수신 코드가 새 계약을 반영했다면 유효한 이메일·코드 헤더 요청은 401을 통과해야 합니다.
현재는 유효한 참가자 정보를 사용하지 않았으므로, 실제 접수 확인에는 참가자 이메일과 코드로
한 번의 테스트가 더 필요합니다.

이메일·6자리 코드는 제공받지 않았으므로 실제 인증 제출은 실행하지 않았습니다.
새 하네스 계약은 `X-Participant-Email`, `X-Participant-Code`, `X-Participant-Workshop` 헤더로
이메일별 코드를 전달합니다. 운영측은 이 세 값을 확인한 뒤에만 `/api/lite` 본문을 처리해야 합니다.

## 운영측이 준비할 것

1. 참가자 계정·행사 이름·6자리 코드와 1:1 카카오 실습 대화방.
2. 참가자 `operator-handoff.json`의 4명/순서에 맞춘 운영측 후보 응답 프로세스.
   `OOO님 면접 시작하겠습니다`에 해당 후보를 준비하고,
   `수고하셨습니다` 뒤 다음 후보 평가 동안 기다려야 합니다.
3. [founder-light-1 제출 계약](operator-api.md)을 받는 `/api/lite` 배포와 세 필드 접수 응답.
   해당 주소를 `operator.url` 기본값으로 설정했습니다. 참가자 계정의 이메일·6자리 코드를
   제출 헤더에서 확인하고, 토큰이나 참가자 로그인 endpoint는 사용하지 않아야 합니다.

## 수신 소스와의 호환성 확인

운영측에 추가된 `founder_contract.py`와 `lite_gateway.py`를 읽기 전용으로 확인했습니다.
초기 하네스의 `insights.sha256`은 수신부에서 extra_forbidden 오류가 났습니다.
새 제출은 `insights.markdown`만 보내고 원문 해시는 네 번째 면접의 insights_after_sha256로
검증하도록 맞췄습니다. 최종 제출 인증은 이메일·코드 헤더로 바꿨으며, 기존 Bearer 토큰은 사용하지 않습니다.
실제 종료 안내가 제한 시간보다 늦으면 수신부가 요구하는 진행 예외 메모를 남깁니다.

이 문서의 변경은 참가자 하네스와 계약 문서에 반영된 상태입니다. 읽기 확인한 운영측
`lite_gateway.py`는 아직 Bearer 제출 전용 토큰을 확인하므로, 운영측 수신부도 위 세 헤더를
확인하도록 수정·배포해야 실제 제출이 가능합니다. 외부 운영 소스는 이 워크트리에서 수정하지 않았습니다.

합성 면접 4명·사용자 평가·최종 인사이트로 생성한 본문을 운영측 실제 `validate_final`에
전달하는 검사는 로컬 임시 디렉터리에서 수행했습니다. 실제 참가자 제출을 만들거나 전송하지 않았습니다.

일반 서버의 배정·interview_id·Actor API를 참가자의 무작위 4명 배정과 같다고 취급하지 않습니다.
참가자는 일반 서버 회차를 임의로 시작하거나 다른 배정의 Actor를 호출하지 않습니다.
서버 기본 주소만으로 후보 응답 프로세스나 최종 수신부가 생기지는 않습니다.
수신 경로가 없으면 네 번째 평가 후 최종 파일을 남기고 submission_pending으로 유지합니다.
정상 접수 영수증을 검증하기 전에는 전체 완료로 표시하지 않습니다.
